# TrustRelay v0.9 — Webhooks, Notifications, Organization Roles, Compliance & Audit Exports

Date: 2026-10-01

## Release scope

v0.9 adds the operational and compliance layer required for an institution to run TrustRelay continuously rather than treating each verification as an isolated transaction.

The release adds four connected capabilities:

1. signed webhook delivery with retry and dead-letter handling
2. in-app notifications and notification preferences
3. explicit organization role-based access control
4. private, tamper-evident compliance/audit exports

v0.9 preserves the v0.8 identity/evidence controls and the existing Partner API route.

## Organization roles

Roles:

- owner
- admin
- compliance
- verifier
- developer
- auditor

### Owner

Permissions include:

- organization management
- members and roles
- API keys
- webhooks
- decisions
- evidence
- audit read/export
- notification administration
- ownership transfer

Only an owner may transfer ownership.

### Admin

Broad operational permissions, but an admin cannot:

- transfer ownership
- change the owner
- promote another member to admin
- manage another admin

### Compliance

Can:

- read decisions
- read/review evidence
- read organization audit history
- create compliance exports

Cannot manage members, API keys, or webhook endpoints.

### Verifier

Can:

- evaluate authority
- read decisions
- request/review/read evidence

Cannot access organization audit history, API-key metadata, webhook configuration, team administration, or compliance exports.

### Developer

Can:

- manage Partner API keys
- manage webhooks
- read decisions
- read organization audit history

Cannot access evidence workflows or membership administration and cannot generate compliance exports.

### Auditor

Can:

- read decisions
- read evidence
- read audit history
- generate compliance exports

Cannot mutate organizational configuration.

## Least-privilege dashboard boundary

v0.9 does not rely on hidden buttons alone.

The authenticated organization dashboard strips unauthorized data before returning JSON:

- no API-key list without `api_keys.manage`
- no member/invitation list without `members.manage`
- no webhook endpoints, deliveries, or attempts without `webhooks.manage`
- no evidence requests without `evidence.read`
- no organization audit events without `audit.read`
- no export history without `audit.export`

The Verifier Portal navigation uses the same permission map.

## Organization membership lifecycle

Supported operations:

- invite
- accept invitation
- change role
- disable access
- restore access
- remove member
- transfer ownership

Membership status:

- active
- disabled
- removed

A removed account must be invited again before rejoining.

Reaccepting a new invitation clears stale disabled/removal metadata.

There is exactly one active owner per organization.

Ownership transfer atomically changes:

- current owner -> admin
- target active member -> owner

Relevant organization events are appended to the organization audit chain and surfaced through notifications/webhooks.

## In-app notifications

v0.9 implements an authenticated in-app notification inbox for both the consumer app and Verifier Portal.

Categories:

- authority
- evidence
- identity
- organization
- webhook
- compliance
- security

Severity:

- info
- success
- warning
- critical

State:

- unread
- read
- archived

Users may disable individual in-app notification categories.

When a category is disabled, new notifications in that category are suppressed rather than created and hidden.

### Current delivery boundary

v0.9 implements **in-app notifications**.

It does not claim outbound email, SMS, or push notification delivery. Those require a future provider integration.

## Signed webhooks

Webhook signing secrets remain encrypted in Supabase Vault.

Raw signing secrets are returned only:

- when an endpoint is created
- when the secret is rotated

The secret is never returned by the event queue or dashboard.

### Supported webhook events

- `decision.created`
- `grant.revoked`
- `credential.revoked`
- `evidence.requested`
- `evidence.submitted`
- `evidence.resolved`
- `organization.member.invited`
- `organization.member.joined`
- `organization.member.role_changed`
- `organization.member.disabled`
- `organization.member.restored`
- `organization.member.removed`
- `organization.ownership.transferred`
- `identity.assurance.changed`
- `compliance.export.ready`
- `webhook.test`

A legacy `organization.member.enabled` catalog alias remains accepted for compatibility.

### Signature

Headers:

- `X-TrustRelay-Event`
- `X-TrustRelay-Delivery`
- `X-TrustRelay-Timestamp`
- `X-TrustRelay-Signature`

Signature input:

`<timestamp>.<raw_body>`

Algorithm:

HMAC-SHA256

Header format:

`X-TrustRelay-Signature: v1=<hex>`

### Delivery engine

Canonical delivery is database-driven through Supabase `pg_net`.

A once-per-minute Cron job executes:

`trustrelay_webhook_maintenance_v09()`

The maintenance job:

1. reconciles finished HTTP requests
2. records individual attempt history
3. schedules retries
4. dispatches due deliveries

Retry schedule is bounded exponential backoff:

- 1 minute
- 5 minutes
- 30 minutes
- 2 hours

A delivery enters `dead_letter` after its configured maximum attempts.

Dead-letter events:

- notify owner/admin/developer roles
- append a hash-chained organization audit event

A webhook subscription is automatically paused when its consecutive-failure threshold is reached.

Authorized developers/admins/owners can:

- test an endpoint
- pause
- resume, including auto-disabled endpoints
- retry a dead-letter/retrying delivery
- rotate the signing secret
- permanently revoke the endpoint

### SSRF controls

Webhook endpoint creation rejects obvious:

- localhost targets
- `.localhost`
- `.local`
- `.internal`
- private IPv4 ranges
- link-local IPv4
- URL user-info
- literal IPv6 hosts

This is defense in depth; production infrastructure should also apply outbound network controls.

## Organization audit chain

Administrative/compliance events use an organization-specific SHA-256 hash chain.

Examples include:

- invitation created/accepted
- role changes
- member disable/restore/remove
- ownership transfer
- evidence workflows
- webhook lifecycle changes
- webhook dead-letter events
- compliance export requests/results
- identity-assurance changes relevant to an organization

The organization verifier recomputes every event hash and predecessor link.

It reports:

- `valid`
- event count
- head hash
- failing event ID/hash details when invalid

## Authorization audit chain

Authorization decisions continue to use the original global TrustRelay authorization audit chain.

The current global status helper verifies predecessor-link continuity and reports `linked`.

This is intentionally described differently from the organization audit verifier: v0.9 does not relabel link continuity as full event-payload recomputation.

## Compliance exports

Canonical Edge Function:

`trustrelay-compliance-export-v09`

It requires an authenticated TrustRelay user and organization `audit.export` permission.

Actions:

- `create`
- `list`
- `download`

### Formats

- JSON
- CSV

### Date range

Default:

last 30 days through current time

Maximum:

366 days

### Scopes

- `decisions`
- `audit_events`
- `webhooks`
- `members`
- `evidence`
- `api_keys`
- `notifications`
- `all`

### Data minimization

Exports do not include:

- raw Partner API keys
- API-key hashes
- webhook signing secrets
- private signing keys
- Auth tokens
- raw identity-document file bodies

Evidence export data contains request/document references and workflow metadata rather than private file bytes.

### Private storage

Bucket:

`trustrelay-compliance-exports`

Configuration:

- private
- JSON/CSV only
- 25 MB bucket maximum
- generated output additionally capped by the Edge exporter
- private signed download URL valid for five minutes
- export record expires after 24 hours

### Artifact integrity

The exact generated artifact bytes are SHA-256 hashed.

The source dataset is also SHA-256 hashed in the manifest.

### Export hash chain

Each ready export participates in a per-organization export chain:

`SHA256(previous_export_hash | export_id | organization_id | content_sha256 | manifest_json | created_at)`

Stored fields include:

- content SHA-256
- previous export hash
- current export hash
- row count
- size
- manifest
- completion time
- expiration time

A ready export also generates:

- organization audit event
- in-app notification
- `compliance.export.ready` webhook event

## Retired test/superseded surfaces

The temporary Edge webhook worker is retired. Delivery is handled by database maintenance.

The test webhook receiver is retired.

The older `trustrelay-compliance-v09` gateway is retired in favor of:

`trustrelay-compliance-export-v09`

Retired Edge surfaces require JWT verification and return HTTP 410 if reached by an authorized caller.

## Security boundary

- Browser: publishable Supabase key + user JWT
- Partner server: TrustRelay partner API key
- External Partner API keys: hash-only storage
- Webhook signing secrets: Supabase Vault
- Compliance artifacts: private Storage
- Compliance download: five-minute signed URL
- Organization data: server-enforced role/permission filtering
- Sensitive service functions: service-role only

## Known Auth warning

Supabase Security Advisor still reports:

`Leaked Password Protection Disabled`

This feature is unavailable on the current Free plan.

TrustRelay user-facing authentication is passwordless magic-link/OTP and does not accept application passwords.
