# TrustRelay v1.0 Incident Response Runbook

Status: production-candidate procedure — requires named incident owner and monitored security contact before activation.

## Severity

- SEV-1: confirmed unauthorized access to identity evidence, signing keys, production API secrets, or widespread authorization integrity failure.
- SEV-2: material service outage, repeated webhook/data-integrity failure, suspected account/org compromise with limited scope.
- SEV-3: contained defect or suspicious activity without confirmed sensitive-data exposure.

## Immediate actions

1. Preserve evidence. Do not delete audit, decision, webhook, billing, or relevant infrastructure logs.
2. Contain access. Revoke affected API keys, webhook secrets, organization memberships, credentials or signing keys as appropriate.
3. If authority integrity may be affected, suspend relevant grants or production organization access rather than guessing.
4. Identify affected data subjects, organizations, time window and systems.
5. Record a UTC incident timeline, actions, decision makers and evidence hashes where available.
6. Escalate to the named security/incident owner and legal counsel for notification analysis.

## TrustRelay-specific controls

- Credential/grant revocation is immediate and live verification checks revocation state.
- Organization members can be disabled without deleting membership history.
- API keys and webhook secrets can be revoked/rotated.
- Organization activity uses a SHA-256 hash chain.
- Authorization decisions retain evaluation and audit hashes.
- Compliance exports can preserve bounded audit evidence without exporting private identity-document bodies.

## Notification decision

Do not make a legal breach-notification determination solely from this runbook. Counsel must determine obligations, recipients and deadlines based on the incident and applicable law/customer agreements.

## Recovery

Before reopening a contained workflow:
- rotate compromised credentials/secrets;
- verify relevant audit chains;
- verify production runtime/billing state;
- confirm affected code/configuration is fixed;
- test authorization decisions and webhook signatures;
- document the recovery decision.

## Post-incident

Complete root cause, corrective actions, control owner and target date. Update the risk register/readiness controls where the event exposed a missing control.
