# TrustRelay Partner API v0.7

## Purpose

TrustRelay v0.7 gives institutions one question to ask before acting on a representative's request:

> Is this exact person authorized to perform this exact action against this exact resource, under the grant's current rules, right now?

The Partner API verifies the TrustRelay ES256 credential, checks its live grant/revocation state, evaluates policy, and records an auditable **ALLOW**, **DENY**, or **ESCALATE** decision.

## Base URL

`https://awrradmcwgeepwwdrbzi.supabase.co/functions/v1/trustrelay-partner-v07`

The machine-readable contract is published at:

`/verifier/openapi.json` on the TrustRelay staging site.

## Authentication

Create a partner API key in the Verifier Portal and send it on:

`X-TrustRelay-Key: tr_test_...`

Partner keys are intended only for server-side systems. Never place them in browser JavaScript, mobile applications, public repositories, logs, URLs, or query strings.

TrustRelay stores only the SHA-256 hash of an external partner API key. The raw key is shown once at creation.

Sandbox organizations receive `tr_test_` keys. Production/live keys are reserved for future production activation.

## Evaluate authority

`POST /v1/decisions/evaluate`

Required fields:

- `requestId` — institution-generated idempotency key
- `credential` — signed TrustRelay authority credential
- `action`
- `resource`

Optional fields:

- `correlationId`
- `amount`
- `currency`
- `evidence`

Example:

```json
{
  "requestId": "req_123",
  "correlationId": "case_4501",
  "credential": "eyJ...",
  "action": "pay_bill",
  "resource": "checking:1234",
  "amount": 175,
  "currency": "USD",
  "evidence": {
    "invoiceId": "INV-1042"
  }
}
```

The API does **not** persist the raw credential token in the authorization request evidence. It stores a SHA-256 credential fingerprint, the verified credential JTI, the authority policy snapshot, and the decision evidence.

### Idempotency

Within an organization, reusing the same `requestId` returns the previously persisted decision rather than producing a second decision.

## Decision outcomes

### ALLOW

The signed credential is valid and the action/resource/rules are satisfied.

Typical reason:

- `POLICY_SATISFIED`

### DENY

The institution should not perform the operation.

Examples:

- `CREDENTIAL_REVOKED`
- `ACTION_PROHIBITED`
- `ACTION_NOT_ALLOWED`
- `RESOURCE_NOT_ALLOWED`
- `CURRENCY_NOT_ALLOWED`
- `AMOUNT_ABOVE_LIMIT`

### ESCALATE

TrustRelay cannot automatically authorize the operation and the institution should route it to a review/evidence workflow.

Examples:

- `AMOUNT_ABOVE_LIMIT` where the grant requests escalation
- `EVIDENCE_REQUIRED`
- `POLICY_REVIEW_REQUIRED`
- `MANUAL_REVIEW_REQUIRED`

## Retrieve a decision

`GET /v1/decisions/{requestId}`

Requires a key with `decisions:read`.

## API-key scopes

v0.7 currently supports:

- `decisions:read`
- `decisions:write`

Organization owners, admins, and developers can create/revoke partner API keys. Verifiers and auditors cannot create keys.

## Verifier Portal

The browser-based Verifier Portal does **not** receive a partner API key.

TrustRelay creates an internal organization portal key and encrypts it in Supabase Vault. The authenticated portal bridge retrieves that key server-side, calls the same Partner API used by external integrations, and records the decision source as `portal`.

This ensures the visual portal and external API share one authorization engine.

## Signed webhooks

Supported events:

- `decision.created`
- `grant.revoked`
- `credential.revoked`

Webhook endpoint URLs must be HTTPS. Obvious localhost, link-local, private IPv4, `.local`, URL-userinfo, and literal IPv6 targets are rejected to reduce SSRF risk.

Webhook signing secrets are generated once, returned once to the organization administrator/developer, and encrypted at rest in Supabase Vault.

Headers include:

- `X-TrustRelay-Event`
- `X-TrustRelay-Delivery`
- `X-TrustRelay-Timestamp`
- `X-TrustRelay-Signature: v1=<hex>`

Signature input:

`<timestamp>.<raw_request_body>`

Algorithm:

HMAC-SHA256 using the webhook signing secret.

Consumers should use constant-time comparison and reject stale timestamps.

## Audit evidence

Each authorization decision records:

- organization
- partner API key ID
- request ID / correlation ID
- action/resource
- decision / reason code
- grant and credential references
- policy snapshot
- evidence metadata
- request fingerprint
- evaluation hash
- linked audit-event ID/hash
- decision source (`api` or `portal`)
- latency
- timestamp

## Rate limiting

Partner API keys are currently limited to 120 requests per 60-second window by default. Rate state is organization-key specific.

## Security boundary

- Browser: Supabase publishable key + user JWT only.
- Partner servers: TrustRelay partner API key only.
- Supabase server code: secret key and Vault access.
- External partner API keys: hash-only storage.
- Internal portal API key: encrypted in Vault.
- Webhook signing secrets: encrypted in Vault.
- Private signing JWK: encrypted in Vault.
