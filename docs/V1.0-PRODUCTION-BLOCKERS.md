# TrustRelay v1.0 Remaining Production Blockers

Date: 2026-10-01 / 2026-10-02 UTC crossover

TrustRelay's current technical production candidate remains intentionally fail-closed. The items below require human ownership, provider configuration, legal/business approval, credentials not available to the automation, or explicit cost/organization confirmation.

## Infrastructure / provider decisions

### Production Supabase isolation
Current production-readiness control: `production_backend_isolation = fail`.

A separate production Supabase project must be created. Creation requires explicit confirmation of:
- target Supabase organization;
- provider-reported project cost.

Do not repurpose `trustrelay-staging` as production.

### Backup / recovery
Current control: `backup_recovery = fail`.

The current staging organization is on the Free plan and does not provide validated production backup/restore evidence. Production requires:
- an approved backup mechanism;
- off-project/off-site recovery posture appropriate to the business;
- a completed restore test.

### Database network restrictions
Current control: `database_network_restrictions = unknown`.

Supabase exposes this through dashboard/Management API, but the connected project-management toolset does not expose the current setting. Production must explicitly verify the allowed CIDRs on the final production project.

### Database SSL enforcement
Current control: `database_ssl_enforcement = unknown`.

Supabase supports an explicit SSL-enforcement setting, but the connected toolset does not expose its current value. Production must verify/enable it on the final project and use an appropriate client SSL mode.

### Auth abuse protection
Current control: `auth_abuse_protection = unknown`.

Supabase provides endpoint rate limits and optional CAPTCHA/Turnstile protection. The connected toolset does not expose the current CAPTCHA/bot-protection setting. Production must verify rate limits and the chosen abuse-control posture.

### Custom SMTP
Current control: `custom_smtp = fail`.

A production transactional email provider, sender domain, credentials, and monitored delivery/bounce process must be selected/configured.

### Custom domain
Current control: `custom_domain = fail`.

Requires ownership/control of the production domain and DNS changes.

### Malware scanning
Current control: `malware_scanning = fail`.

Evidence uploads currently enforce type, size, hash, access control, and review state, but `basic_validated` is not malware scanning. A production malware-scanning provider/service and failure policy must be selected.

## Human governance

### Reviewer governance
Current control: `reviewer_governance = fail`.

Production requires at least two explicitly approved, trained, unexpired reviewers. Do not auto-appoint pilot users or developers as identity reviewers.

### Security contact
Current control: `security_contact = fail`.

A real monitored security contact must be designated and verified operationally.

### Privacy request process
Current control: `privacy_request_process = fail`.

A monitored privacy contact and an approved jurisdiction-aware deadline policy are required. TrustRelay intentionally does not invent legal deadlines.

### Incident-response approval
Current control: `incident_response_plan = fail`.

The technical runbook exists in `docs/V1.0-INCIDENT-RESPONSE.md`, but production activation requires named owners/escalation paths and organizational approval.

## Legal / policy decisions
