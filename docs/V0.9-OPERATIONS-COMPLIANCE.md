# TrustRelay v0.9 — Operations, Notifications, RBAC, and Compliance Exports

Date: 2026-10-01

## Release scope

v0.9 turns the v0.8 identity/evidence platform into an operational institutional system.

The release adds four connected capabilities:

1. Durable, signed partner webhooks with retries and dead-letter evidence.
2. In-app notifications for consumer and institutional users.
3. Permission-based organization roles and auditable member lifecycle.
4. Tamper-evident compliance/audit exports in private storage.

Existing v0.8 identity, assurance, document, credential, and evidence boundaries remain in place.

Owner protections:

- Only an owner can grant or remove the owner role.
- The final active owner cannot be demoted.
- The final active owner cannot be disabled.
- Member disable preserves membership history instead of deleting the record.

Role changes and disables are appended to the organization audit chain and generate notifications.

## Organization audit ledger

Table:

`organization_audit_events`

Each organization has an independent SHA-256 hash chain.

An event stores:

- actor account
- event type
- target type/id
- metadata
- previous event hash
- current event hash
- timestamp

Appending an event takes an organization-specific PostgreSQL advisory lock before reading the current chain head.

The verifier portal can run an independent chain verification using:

`trustrelay_verify_org_audit_chain_v09`

Current event coverage includes:

- organization creation
- API-key creation/revocation
- webhook creation/revocation/secret rotation/test/retry
- organization invitation acceptance
- role changes and member disables
- authorization decisions
- evidence requests/submissions/resolutions
- compliance export requests/readiness

## Durable webhooks

Webhook secrets remain encrypted in Supabase Vault.

Webhook endpoints must use HTTPS. TrustRelay rejects obvious localhost/private-network literal destinations and URL user-info.

### Canonical body

The caller's JSON is parsed to JSONB and serialized to one canonical body before queueing.

The SHA-256 payload hash and the HMAC signature therefore cover the same body sent through `pg_net`.

### Signature

Headers:

- `X-TrustRelay-Event`
- `X-TrustRelay-Delivery`
- `X-TrustRelay-Timestamp`
- `X-TrustRelay-Signature`

Signature input:

`<timestamp>.<raw request body>`

Algorithm:

HMAC-SHA256

Header representation:

`v1=<64 lowercase hex characters>`

### Delivery lifecycle

Statuses:

- pending
- dispatched
- retrying
- delivered
- dead_letter

Default maximum attempts:

5

Retry schedule after failed attempts:

1. about 1 minute
2. about 5 minutes
3. about 30 minutes
4. about 2 hours
5. dead-letter

Each HTTP attempt is separately retained in `webhook_delivery_attempts`.

Repeated failures across deliveries can automatically pause a subscription at its failure threshold.

Operational controls:

- test delivery
- rotate signing secret
- revoke endpoint
- manually retry retryable/dead-letter delivery
- attempt history
- payload SHA-256
- dead-letter notification

Rotating a signing secret also clears a failure pause and resets consecutive failures.

### Scheduler

`pg_cron` job:

`trustrelay-webhook-maintenance-v09`

Schedule:

every minute

Each run:

1. reconciles completed `pg_net` HTTP requests
2. dispatches newly due or retrying deliveries

### Deliberate exclusion

Compliance exports do not contain private identity-document bodies.

Evidence-request exports include workflow metadata and attached TrustRelay document IDs, not the underlying private ID/passport/image/PDF bytes.

### JSON output

JSON includes a manifest plus structured export data.

### CSV output

CSV is a normalized event-style file with:

- record_type
- record_id
- occurred_at
- payload_json

### Integrity

The service records:

- source dataset SHA-256
- exact output SHA-256
- per-section record counts
- total record count
- byte size
- organization audit-chain verification result/head hash
- generation timestamp
- schema version

The exact exported bytes are hashed before metadata is finalized.

Downloads use a fresh private signed URL valid for 300 seconds.

Export metadata expires after seven days.

## Security boundaries

New v0.9 public data tables use RLS and restrictive deny policies for `anon` and `authenticated`.

Browser clients do not receive:

- Vault secrets
- service-role/secret Supabase keys
- compliance bucket direct access
- unrestricted table access

Public application RPCs use signed-in identity and private helper functions for authorization.

The public permission endpoint is a SECURITY INVOKER wrapper; the security-definer portion is in the private schema.

### Remaining webhook egress consideration

The endpoint validator blocks obvious local/private literal destinations, but production deployments should add infrastructure-level outbound network policy or DNS-resolution validation if strict SSRF resistance is required against DNS rebinding.

## Current Auth advisory

Supabase Security Advisor still reports:

`Leaked Password Protection Disabled`

This is the existing Free-plan Auth advisory.

TrustRelay's user-facing authentication remains passwordless magic-link/email OTP, so application users do not create TrustRelay passwords.
