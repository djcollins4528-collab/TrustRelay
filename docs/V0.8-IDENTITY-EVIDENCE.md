# TrustRelay v0.8 — Identity Proofing, KYC Adapter, and Evidence Workflow

Date: 2026-10-01

## Release scope

v0.8 adds high-assurance identity and private evidence workflows without weakening the passwordless authentication or v0.7 institutional authorization model.

The implementation deliberately distinguishes:

1. **Authentication** — control of the signed-in email/session.
2. **Identity assurance** — how strongly TrustRelay has verified the person behind that account.
3. **Authority** — what that verified person is allowed to do.
4. **Evidence** — documents supporting identity or a specific authorization request.

## Assurance levels

TrustRelay currently uses four levels:

- `none`
- `email_verified`
- `document_verified`
- `high_assurance`

### document_verified

Requires an identity-proofing session with approved government-ID evidence.

### high_assurance

Requires approved government-ID evidence plus approved address evidence in the manual TrustRelay review path, or an approved result from a configured high-assurance provider adapter.

### Important limitation

v0.8 does **not** claim biometric face matching, liveness detection, sanctions screening, AML screening, or regulatory KYC certification. No external KYC vendor is currently hard-wired into the product.

Instead, v0.8 provides:

- an independent TrustRelay manual reviewer path
- a service-role-only provider-result adapter
- provider reference and result hashing
- a strict assurance state machine
- an explicit consented requested assurance level

A later provider integration can call the adapter only after its own webhook/authenticity checks.

## Self-review protection

Normal users cannot approve documents or promote their own assurance.

Identity reviewers must be explicitly provisioned in the private `identity_reviewers` table through the service-role-only reviewer provisioning function.

The review functions independently reject a reviewer attempting to review a document or proofing session belonging to their own TrustRelay person.

## Private document storage

Bucket:

`trustrelay-evidence`

Properties:

- private
- 10 MB object limit
- allowed MIME types:
  - application/pdf
  - image/jpeg
  - image/png
  - image/webp

The browser does not receive a permanent public URL.

Upload workflow:

1. Authenticated user requests document preparation.
2. TrustRelay creates the document metadata and a random storage key.
3. Server returns a short-lived signed upload token.
4. Browser uploads directly to the private bucket.
5. User requests finalization.
6. TrustRelay downloads the object server-side.
7. TrustRelay verifies actual object size/type and computes SHA-256.
8. Integrity metadata is recorded before review submission.

Download workflow:

- Access is re-authorized server-side.
- TrustRelay creates a five-minute signed download URL.
- Identity reviewers can access review-queue evidence.
- An institution can access only a document that a user explicitly attached to that institution's evidence request.

### Malware-scanning boundary

v0.8 performs type, size and SHA-256 integrity validation.

A dedicated malware/antivirus scanning provider is **not yet integrated**, so `scan_status=basic_validated` must not be represented as antivirus-clean.

## Manual identity proofing state machine

Statuses:

- collecting
- submitted
- in_review
- approved
- rejected
- expired
- cancelled

Submission requirements:

- `document_verified`: at least one finalized government ID or passport
- `high_assurance`: government ID/passport plus address evidence

The reviewer separately decides each document before approving the identity session.

## Provider adapter

Service-role-only function:

`trustrelay_apply_provider_result_v08`

Inputs include:

- proofing session
- provider
- provider reference
- approved/rejected result
- assurance level
- provider result JSON

Protections:

- not callable by anon/authenticated
- result JSON must parse
- provider result is SHA-256 hashed
- assurance cannot exceed/change the user's consented requested assurance level
- assurance events are recorded

## Grant policy extensions

v0.8 adds two optional rules:

### minimumAssurance

Example:

```json
{
  "minimumAssurance": "high_assurance"
}
```

Both principal and representative must currently meet the specified assurance.

If an active grant later falls below the requirement, grant refresh moves it back to:

`pending_verification`

Legacy grants without this rule retain the pre-v0.8 verified-identity behavior.

### requireVerifiedEvidence

Example:

```json
{
  "requireVerifiedEvidence": true
}
```

This is different from ordinary `requireEvidence`.

A request satisfies `requireVerifiedEvidence` only when the Partner API receives TrustRelay document IDs that:

- are linked to that grant
- still exist
- are basic-validated
- were independently reviewer-approved

If none qualify, the authorization result is:

`ESCALATE / VERIFIED_EVIDENCE_REQUIRED`

## Institutional evidence requests

After an institution has evaluated a grant, owner/admin/verifier roles can create an evidence request tied to that grant.

The principal or representative can:

- see the request
- select one of their private finalized documents
- explicitly attach it to the request

Only after that explicit attachment may authorized members of that requesting institution retrieve the file.

Institution roles allowed to view submitted request documents:

- owner
- admin
- verifier
- auditor

Institution roles allowed to resolve a request:

- owner
- admin
- verifier

Resolution:

- satisfied
- rejected

Resolution reason, notes, reviewer account and timestamps are retained.

## Credential behavior

New credentials are still ES256 signed but now use TrustRelay credential version `0.8`.

They include an `assurance_at_issue` snapshot.

Public verification also refreshes the grant's live assurance status before declaring the credential valid and returns current principal/representative assurance separately.

This means an old credential cannot hide a later assurance downgrade.

## Partner API v0.8

Existing route remains stable for compatibility:

`/functions/v1/trustrelay-partner-v07`

Health reports version `0.8.0`.

Evaluation accepts:

```json
{
  "requestId": "req_123",
  "credential": "eyJ...",
  "action": "pay_bill",
  "resource": "checking:1234",
  "amount": 175,
  "currency": "USD",
  "evidence": {
    "invoiceId": "INV-1042"
  },
  "evidenceDocumentIds": [
    "doc_..."
  ]
}
```

Submitted document IDs never bypass access or review state. The server resolves them to approved grant-linked evidence before policy evaluation.

## Reviewer console

Staging route:

`/reviewer/`

The route uses passwordless Auth but is useless without explicit internal reviewer provisioning.

Features:

- review queue
- five-minute private evidence downloads
- document approve/reject
- session approve/reject
- immutable review-event hashes
- self-review rejection

## Verification completed

### Manual high-assurance rollback test

Passed:

- proofing session started in `collecting`
- government ID and address evidence finalized
- proofing submitted
- self-review returned `SELF_REVIEW_FORBIDDEN`
- separate reviewer saw the queue
- government ID approved
- address evidence approved
- proofing approved
- person promoted to `high_assurance`
- two document review events recorded
- one assurance event recorded

Transaction rolled back.

### Provider + grant enforcement rollback test

Passed:

- principal provider result -> `high_assurance`
- representative provider result -> `high_assurance`
- high-assurance grant activated
- representative downgraded -> grant returned to `pending_verification`
- legacy grant without `minimumAssurance` still activated
- provider over-promotion attempt returned `ASSURANCE_CONSENT_MISMATCH`
- provider result SHA-256 recorded

Transaction rolled back.

### Policy evaluator tests

Passed:

- insufficient live assurance -> DENY / IDENTITY_ASSURANCE_INSUFFICIENT
- sufficient live assurance -> ALLOW
- verified evidence missing -> ESCALATE / VERIFIED_EVIDENCE_REQUIRED
- verified evidence supplied -> ALLOW
- legacy rule set -> ALLOW

## Security checkpoint

All newly created public tables use RLS with restrictive deny-to-client policies.

Privileged reviewer/provider functions are protected through private-schema checks or service-role-only execution.

Supabase Security Advisor currently reports only the pre-existing Free-plan Auth warning:

`Leaked Password Protection Disabled`

TrustRelay's user-facing sign-in is passwordless magic-link/OTP.

## Remaining production dependencies

Before describing TrustRelay as regulatory KYC infrastructure in production, add and validate:

- an external identity/KYC provider if required by the target market
- provider webhook signature verification
- malware scanning/quarantine for uploaded documents
- retention/deletion policy automation
- legal/compliance review for document handling
- production reviewer governance and dual-control rules where required
