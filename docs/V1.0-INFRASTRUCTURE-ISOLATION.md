# TrustRelay Infrastructure Isolation Policy

Date: 2026-10-01

## Hard requirement

TrustRelay must remain operationally, commercially, and technically separate from every unrelated brand or business.

Production TrustRelay infrastructure must not reuse another brand's:

- Supabase organization or project
- Stripe account, products, prices, customers, webhooks, tax settings, or billing identity
- domain or DNS zone
- transactional email/SMTP identity
- secrets or API credentials
- legal entity identity unless explicitly approved as TrustRelay's contracting entity
- security/privacy contact identity
- production data stores
- production storage buckets
- production signing/encryption secrets

## Required production boundaries

### Supabase

Create a dedicated TrustRelay Supabase organization and a dedicated production project inside that organization.

The current staging project may continue to exist only as staging until migration is complete. It must not be promoted as the final production backend.

### Stripe

Connect a dedicated TrustRelay Stripe business/account before enabling commercial billing.

Do not configure TrustRelay products or price IDs in any unrelated Stripe account.

### Render

TrustRelay services should reside in a dedicated TrustRelay workspace/environment boundary when the provider account permits it.

Until that workspace is created, the existing staging services remain staging-only and must not be treated as the final production ownership boundary.

### GitHub

The canonical TrustRelay repository remains:

`djcollins4528-collab/TrustRelay`

No TrustRelay production source should be moved into or depend on an unrelated product repository.

### Domain and email

Production must use a TrustRelay-specific domain/DNS configuration and TrustRelay-specific transactional email identity.

### Secrets

Production credentials must be newly generated for TrustRelay. Do not copy unrelated brand credentials into TrustRelay.

## Release-gate enforcement

The following production readiness controls must remain failed until TrustRelay-specific evidence exists:

- `production_backend_isolation`
- `billing_provider`
- `custom_domain`
- `custom_smtp`
- `security_contact`

A control cannot be marked pass merely because an unrelated provider account is technically available.

## Migration rule

When dedicated TrustRelay production accounts are created:

1. provision fresh production infrastructure;
2. apply canonical TrustRelay migrations and Edge Functions from `main`;
3. generate fresh production secrets/keys;
4. configure TrustRelay-only domain, email and billing integrations;
5. run full production validation;
6. only then activate production organizations.

No staging secrets or unrelated-brand secrets should be promoted into production.
