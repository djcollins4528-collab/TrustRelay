# TrustRelay Enterprise SSO v1.3 — Operator Runbook

## Supported identity providers

TrustRelay supports organization-scoped enterprise authentication through:

- Microsoft Entra ID — OIDC available now.
- Okta — OIDC available now.
- SAML 2.0 — architecture is implemented for Entra ID and Okta but remains fail-closed until the Supabase project plan supports SAML and `TRUSTRELAY_SAML_ENABLED=true` is intentionally approved.

OIDC uses Supabase custom providers with PKCE. Client secrets are sent only to the server-side SSO control plane and Supabase Auth; they are not stored in TrustRelay application tables or browser storage.

## Organization onboarding flow

1. An Owner or Admin opens **Verifier Portal → Enterprise SSO**.
2. Choose Microsoft Entra ID or Okta.
3. Configure the identity-provider application using the callback URL displayed by TrustRelay.
4. Enter the provider configuration and one or more organization-owned email domains.
5. TrustRelay creates the provider in a disabled state.
6. Publish the generated TXT challenge at `_trustrelay.<domain>`.
7. Use **Verify domains** after DNS propagation.
8. TrustRelay enables the provider only after all configured domains are verified.
9. Use **Test enterprise sign-in** and complete the TrustRelay portal MFA step.
10. After the exact provider session is verified, an Owner/Admin may switch the organization from optional SSO to required SSO.

## Microsoft Entra ID OIDC

Create a Web application registration and use the exact Supabase callback URI displayed in TrustRelay.

TrustRelay requires:

- Directory (tenant) ID
- Application (client) ID
- Client secret
- Organization-owned email domain(s)

The issuer is derived as:

`https://login.microsoftonline.com/<tenant-id>/v2.0`

TrustRelay validates the tenant ID format before provider creation.

## Okta OIDC

Create an OIDC Web Application and use the exact Supabase callback URI displayed in TrustRelay.

TrustRelay requires:

- Client ID
- Client secret
- Okta issuer URL
- Organization-owned email domain(s)

Accepted issuer hosts are restricted to Okta-controlled domains used by the supported Okta environments.

## Domain ownership verification

Provider activation is intentionally separated from provider creation.

For each configured domain TrustRelay generates a TXT challenge:

- Record type: `TXT`
- Record name: `_trustrelay.<domain>`
- Record value: generated by the SSO control plane

Only a hash of the verification value is retained in TrustRelay's database. The Edge Function performs DNS-over-HTTPS verification and enables the provider only when all configured domains are verified.

Personal email domains such as Gmail, Outlook, Yahoo, iCloud and Proton are rejected.

## Account binding and tenant isolation

Supabase enterprise SSO can create a separate Auth user even when the email address matches an existing passwordless user. TrustRelay therefore uses `account_auth_bindings` to allow more than one authenticated identity to map to one TrustRelay account without replacing the account's original auth identity.

Same-email SSO linking is not sufficient by itself. An SSO identity may attach to an existing TrustRelay account only when:

- the session matches the exact configured provider;
- the email domain matches the exact organization SSO domain; and
- the existing TrustRelay account is already an active member of that organization.

Otherwise TrustRelay fails closed with `ACCOUNT_SSO_LINK_REQUIRES_ORG_MEMBERSHIP`.

## Required-SSO lockout protection

Required SSO cannot be enabled merely because a provider has been configured.

TrustRelay requires:

- verified domain ownership;
- a successful session through the exact configured provider;
- portal MFA/AAL2;
- an active organization Owner with a non-SSO email identity available as a break-glass path.

The organization may return SSO to optional mode before disabling the provider.

## Just-in-time membership

JIT membership is disabled by default.

When intentionally enabled, its default role can only be one of:

- Verifier
- Developer
- Auditor
- Compliance

JIT cannot create Owner or Admin membership.

## SAML plan gate

Supabase project-level SAML SSO requires a supported paid plan. TrustRelay therefore keeps the SAML control plane implemented but disabled by default.

Do not enable `TRUSTRELAY_SAML_ENABLED` until:

1. the relevant Supabase environments support SAML;
2. staging SAML metadata/ACS flow is validated with a real Entra or Okta tenant;
3. domain verification passes;
4. required-SSO and break-glass tests pass;
5. the production release gates are green.

## Release validation

Before promoting an SSO-related release:

1. Security Gates must pass.
2. CodeQL must pass.
3. External staging DAST must pass against the exact staging SHA.
4. Staging must be live on that exact SHA.
5. Staging and production SSO database function fingerprints must match.
6. Repo, staging and production `trustrelay-sso-v13` source must match.
7. Production must be pinned to the approved SHA before deployment.
8. Production DAST must pass after deployment.

Never bypass the approved-commit gate to resolve a deployment race.
