# TrustRelay v1.0 Backup & Disaster Recovery Plan

Status: production-candidate runbook — production backup/PITR controls must be confirmed on the final Supabase plan before activation.

## Recovery objectives

Final RPO/RTO are contractual decisions and are not asserted by this draft.

## Critical state

Highest-priority recovery data:
1. people/accounts and organization membership;
2. authority grants, invitations, credentials, signing-key metadata and revocations;
3. authorization decisions and audit chains;
4. identity/evidence metadata and private Storage objects;
5. webhook subscriptions/delivery evidence;
6. billing/onboarding/legal acceptances;
7. compliance export metadata.

## Recovery process

1. Declare incident and freeze unsafe writes if integrity is uncertain.
2. Confirm latest restorable database point and Storage availability.
3. Restore into an isolated recovery environment first when feasible.
4. Validate referential integrity and RLS policies.
5. Verify organization audit chains and credential/revocation state.
6. Smoke-test passwordless authentication, grant verification, Partner API decisions, evidence access and webhook signing.
7. Rotate any secrets exposed during the incident.
8. Promote recovered environment only after documented validation.

## Required pre-launch evidence

- production Supabase backup/PITR configuration;
- tested restore procedure;
- Storage recovery/replication expectations;
- named owner and escalation path;
- dated recovery exercise result.


## Off-site backup implementation

TrustRelay uses a dedicated Cloudflare R2 bucket as the planned off-site backup destination.

Design:
- production and staging snapshots use separate object prefixes;
- R2 jurisdiction must be `us`;
- R2 bucket access is private and uses a bucket-scoped Object Read & Write token;
- R2 provides provider-managed AES-256 encryption at rest and TLS in transit;
- canonical schema/Edge Function source remains in the TrustRelay GitHub repository;
- backup payloads contain application data, selected Auth identity rows, and Supabase Storage objects;
- ephemeral Auth sessions, refresh tokens, Edge Function secrets, plaintext Vault secrets, and live secret material are intentionally excluded and must be rotated/reprovisioned during recovery;
- each exported object has a SHA-256 checksum and the completed snapshot has a manifest checksum;
- an integrity-recovery rehearsal re-downloads the manifest and every snapshot object, recomputes hashes, parses table pages, and records evidence.

Implementation:
- migration: `0027_v10_offsite_backup_control_plane.sql`
- Edge Function: `trustrelay-backup-v10`
- backup metadata: `public.backup_runs`
- recovery-test evidence: `public.backup_restore_tests`
- scheduled trigger: `trustrelay-offsite-backup-v10` after R2 configuration is complete.

Required production Vault entries:
- `trustrelay_r2_account_id`
- `trustrelay_r2_access_key_id`
- `trustrelay_r2_secret_access_key`
- `trustrelay_r2_bucket`
- `trustrelay_r2_jurisdiction` = `us`

The backup scheduler must remain disabled until all required R2 configuration exists and the first manual backup plus integrity rehearsal succeed.
