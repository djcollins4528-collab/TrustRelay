## Identity assurance model

Levels:

1. none
2. email_verified
3. document_verified
4. high_assurance

v0.8 preserves passwordless email magic-link/OTP authentication and treats identity assurance as a separate, revocable state.

## KYC/provider adapter

Implemented service-role-only provider result path:

- provider identifier
- provider reference
- approved/rejected outcome
- provider result JSON
- SHA-256 provider result hash
- assurance promotion
- assurance audit event
- consent-level enforcement

The provider cannot promote beyond the requested assurance level. A mismatched promotion returns:

ASSURANCE_CONSENT_MISMATCH

No external KYC vendor is configured in v0.8.

TrustRelay does not currently claim:

- biometric face matching
- liveness detection
- sanctions screening
- AML screening
- regulatory KYC certification

## Private evidence storage

Bucket: trustrelay-evidence

Verified configuration:

- public: false
- max size: 10,485,760 bytes
- MIME allowlist:
  - application/pdf
  - image/jpeg
  - image/png
  - image/webp

There are no permanent public evidence URLs.

Signed upload tokens are used for browser upload.

Signed downloads expire after five minutes.

v0.8 currently performs type, size, and SHA-256 validation. Dedicated malware/antivirus scanning is not yet integrated and the application explicitly does not label basic validation as an antivirus scan.

## Grant policy extensions

### minimumAssurance

An optional grant rule requiring both principal and representative to continuously meet a specific assurance level.

If either party later drops below the configured minimum, refresh moves an active grant back to:

pending_verification

Legacy grants without minimumAssurance retain their prior verified-identity behavior.

### requireVerifiedEvidence

An optional rule requiring independently reviewer-approved TrustRelay evidence linked to the same grant.

If no qualifying document is provided:

ESCALATE / VERIFIED_EVIDENCE_REQUIRED

## Institutional evidence workflow

Implemented:

1. Institution evaluates a grant.
2. Owner/admin/verifier may create an evidence request.
3. Principal or representative sees the request.
4. User explicitly attaches one of their finalized private documents.
5. Only then can the requesting organization access that specific private file.
6. Owner/admin/verifier can mark the request satisfied or rejected.
7. Auditor can view explicitly shared evidence but cannot resolve the request.

Unattached identity documents remain inaccessible to institutional users.
