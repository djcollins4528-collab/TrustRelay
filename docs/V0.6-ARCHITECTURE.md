# TrustRelay v0.5.1 / v0.6 Staging Architecture

## v0.5.1 — Decision Engine Security Hardening

The v0.5 decision engine remains live on Render:

- Service: `trustrelay-api-staging`
- Region: Virginia
- Engine: `0.5.0`
- Public health path: `/healthz`

Render no longer points directly at privileged Supabase RPCs. Its database base URL is the Supabase Edge bridge `trustrelay-db-v051`.

The v0.5 partner RPC wrappers were converted to `SECURITY INVOKER`. Supabase's security advisor reports zero findings after this cutover.

## v0.6 — Principal / Representative Workflow

### Authenticated Edge Functions

All of these require a valid Supabase Auth JWT:

- `trustrelay-profile-v06`
  - POST: bind the authenticated Supabase user to a TrustRelay account/person.
  - GET: list authority grants where that person is principal or representative.
- `trustrelay-grant-create-v06`
  - POST: create a scoped authority grant and one-time representative invitation token.
- `trustrelay-invite-accept-v06`
  - POST: accept an invitation. The invitation email must match the authenticated account email.
- `trustrelay-grant-revoke-v06`
  - POST: principal-only grant revocation; active credentials are revoked transactionally.
- `trustrelay-credential-issue-v06`
  - POST: issue a signed authority credential for an active grant.

### Public Edge Functions

- `trustrelay-jwks-v06`
  - Returns active/retired ES256 public JWKs for independent verification.
- `trustrelay-credential-verify-v06`
  - Verifies token signature, expiry/not-before, stored-token identity, credential status, signing-key status, live grant status, and revocation state.

### Retired Prototype Endpoints

The earlier `trustrelay-create-grant-v06` and `trustrelay-signing-bootstrap-v06` endpoints now return HTTP 410 and require JWT validation.

## Grant Lifecycle

`draft -> pending_acceptance -> pending_verification -> active -> revoked/expired`

A representative cannot accept an invitation for a different email address.

After acceptance, the grant becomes:

- `active` when both participant identities are verified.
- `pending_verification` otherwise.

A signed credential cannot be issued while the grant is not active.

## Signed Authority Credentials

Credentials use:

- Algorithm: ES256 / NIST P-256
- Format: compact JWS/JWT
- Type: `trustrelay-authority+jwt`
- Issuer: `https://trustrelay.app`
- Audience: `trustrelay-authority`
- Key identifier: `kid`
- Unique credential identifier: `jti`
- Embedded grant version and canonical policy hash
- Maximum credential lifetime: 24 hours, bounded by grant expiration

The first credential issuance automatically creates the first P-256 key pair if no active signing key exists.

The private JWK is stored encrypted in Supabase Vault. The normal `signing_keys` table stores only the public JWK, public thumbprint, status, and Vault reference.

## Revocation

Revoking a grant:

1. Marks the grant revoked.
2. Revokes all active credentials for that grant.
3. Writes credential revocation rows.
4. Revokes any still-pending invitation.
5. Causes subsequent credential verification to fail even when the ES256 signature itself is cryptographically valid.

## Security State

- RLS enabled across exposed public tables.
- New v0.6 workflow/signing tables deny direct anon/authenticated table access.
- Privileged workflow RPCs are service-role only.
- User-facing mutations are mediated by JWT-protected Edge Functions.
- Public verification endpoints expose no private signing material.
- Supabase security advisor: zero findings as of v0.6 staging.
