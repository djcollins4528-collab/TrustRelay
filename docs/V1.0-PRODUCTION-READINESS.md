## Runtime and webhook egress

The canonical webhook transport is the Supabase Edge Function `trustrelay-webhook-egress-v10` in each dedicated environment.

Dedicated Render services are now provisioned in the TrustRelay workspace `tea-davh5u49v7es73fpppf0`:
- staging: `https://trustrelay-staging.onrender.com`
- production: `https://trustrelay-production.onrender.com`

Both use `djcollins4528-collab/TrustRelay` branch `main`, Virginia, Node, auto-deploy, and environment-specific Supabase URLs/publishable keys.

Production webhook delivery now uses pinned-TLS egress:

- the Edge function resolves destination A/AAAA records immediately before delivery;
- every returned address must pass public-IP validation;
- the TCP socket is opened directly to one validated IP, preventing a second DNS resolution before connect;
- TLS is then negotiated using the original hostname for SNI/certificate validation;
- redirects are rejected rather than followed;
- non-default HTTPS ports are supported only when the resolved address passes the same public-IP validation;
- the internal dispatcher-to-egress call requires a high-entropy Vault-backed secret;
- customer webhook HMAC remains `v1=HMAC_SHA256(<timestamp>.<raw JSON body>)`.

Staging verification passed:

- public HTTPS pinned delivery: HTTP 200;
- private literal target `127.0.0.1`: HTTP 403 `WEBHOOK_TARGET_PRIVATE_NETWORK`;
- redirect target: rejected as `WEBHOOK_REDIRECT_BLOCKED`;
- queue -> existing minute cron -> dispatcher -> pinned-TLS egress -> receiver -> reconciler: delivered in one attempt;
- echoed JSON matched the persisted canonical payload;
- HMAC-SHA256 recomputation matched the echoed signature;
- target User-Agent is `TrustRelay-Webhook/1.0`;
- disposable organization, subscription, delivery, attempt and Vault secret were removed after verification.
