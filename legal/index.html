Security controls

Defense in depth.

TrustRelay applies multiple independent controls across authentication, authorization, data access, service-to-service communication, auditability, deployment, and recovery.

IDPasswordless authentication

User-facing access uses email magic-link/OTP rather than reusable account passwords.

2FHigher-assurance institutional sessions

Sensitive institutional operations use additional session and MFA controls with bounded session lifetime.

RBServer-enforced authorization

Owner, admin, compliance, verifier, developer, and auditor capabilities are enforced on trusted server paths rather than UI-only checks.

1×One-time internal capabilities

Privileged internal requests use short-lived, request-bound, single-consumption capabilities instead of reusable browser-visible secrets.

RLRow-level data controls

Application tables use restrictive access policies and privileged operations remain on trusted service paths.

EVPrivate evidence boundaries

Identity and supporting evidence uses private object storage and explicit institution-sharing workflows.

WHSigned webhook delivery

Webhook secrets are protected, deliveries are signed, retries are tracked, and dead-letter handling is supported.

CISecure delivery pipeline

Security gates, CodeQL, dependency controls, workflow pinning, DAST, and approved-commit production deployment controls protect changes.

DRRecovery controls

Backups, recovery procedures, incident-response documentation, and environment isolation reduce operational blast radius.

Operating architecture

Clear security boundaries.

The current production-candidate architecture keeps browser access, application runtime, privileged backend operations, data storage, and external integrations separated by explicit trust boundaries.

Users & institutionsBrowser / API clients

Passwordless users and scoped institutional integrations enter through public application surfaces.

Application boundaryTrustRelay runtime

Host validation, request hardening, rate limits, security headers, and API mediation are enforced here.

Authorization boundaryTrusted server functions

RBAC, one-time internal capabilities, policy evaluation, evidence workflow, and billing controls execute on trusted paths.

Data boundarySupabase platform

PostgreSQL, authentication, private storage, Edge Functions, RLS, scheduled operations, and audit data.

External servicesStripe / email / webhooks

Purpose-limited integrations operate through scoped credentials and controlled event interfaces.

Data protection

Minimize access. Preserve evidence.

TrustRelay is designed to limit who can access sensitive records while preserving the audit evidence institutions need to explain authorization decisions.

Identity & supporting evidence

Evidence is stored privately, integrity-hashed, and exposed through short-lived access paths. Institutional access requires an explicit evidence workflow rather than broad storage access.

Private storageControlled

Authority & credentials

Delegated grants preserve scope, constraints, status, assurance requirements, and revocation state. Signed credentials can be checked against current live state.

Audit & compliance records
